## 1. 已确认的目标与范围

用户要求按 AI 应用开发类岗位秋招的准企业级项目标准优化，并确认以下四阶段范围：

1. 修复运行正确性：依赖、预算、完成判定、计划恢复、MCP 生命周期。
2. 加固任务执行：独立工作区、原始测试保护、路径边界、运行配置持久化、中断恢复。
3. 补工程规范：可复现依赖、配置、日志、API 鉴权与提交限流、CI、Docker。
4. 完成交付证据：评测结构化输出、控制台状态与错误、架构和操作文档。

保留 Python、FastAPI、SQLite、原生单页、自研单 Agent 循环与咨询式 planner。按职责做必要拆分，避免重写整个运行时。

本轮不引入 Redis/Celery、分布式 worker、多租户、多 Agent、向量库、GraphRAG 或前端框架。运行目标为一个可信操作者使用的单机服务；进程级测试执行不宣称能安全执行恶意代码。

- 根据秋招建议与用户随后要求继续的指令，实施计划按“开源自部署完整应用 + 静态只读案例展示”编写；其他人可以按 README 在自己的 Windows/Linux 电脑安装，打开本机 Web 控制台使用。只读展示准备本地产物，不包含未经单独授权的公网发布。

- 真实任务模式支持操作者已有的 OpenAI 兼容本地模型服务，模型计算使用操作者现有硬件；不要求购买显卡，不自动下载大模型。
- 保留远端模型适配能力，但默认关闭远端请求。本轮不调用远端模型；模型名不能作为免费的证明，不依赖免费额度完成验收，也不自动回退到收费模型。
- 零费用交付不包含作者代付并长期运营的公网 SaaS。公共托管不是本轮验收前提，不承诺免费平台长期可用或无限量服务。

- Web ZIP 不允许浏览器指定任意宿主路径；仍为可信操作者使用的本机代码执行，不能直接视为可供匿名公网用户上传执行代码的服务。

## 3. 方案选择

采用“保持业务主线、收口执行入口、逐阶段补齐可靠性”的方案。

仅修局部漏洞无法解决 CLI/API 行为分叉和共享工作区；扩为分布式平台会引入新的运维与一致性问题。当前规模下，统一运行服务、每 run 工作区和 SQLite 原子状态迁移足以支撑本轮目标。

交付分为两个有先后依赖的部分：阶段一、二完成运行可靠性；阶段三、四完成工程与展示。后续实现计划分别列任务，避免一次大改后才验证。

## 4. 组件边界

| 组件 | 职责 |
| --- | --- |
| 配置 | 解析环境变量、校验参数、提供运行设置；不在日志和 API 中输出密钥 |
| 运行服务 | CLI/API 共用的创建、配置解析、运行、恢复与错误处理入口 |
| 工作区管理 | 创建 run 私有副本、校验源路径、生成测试清单、检查漂移 |
| HarnessLoop | 模型决策、工具执行与检查点编排，保留依赖注入 |
| 计量器 | 持久记录调用用量，提供累计值和预算判断 |
| 工具注册表 | 参数验证、权限判定、执行与结果；注册表按 run 隔离 |
| 验证器 | 执行 pytest，返回结构化结果和测试基线完整性结论 |
| 存储 | 版本化 schema、运行状态、配置、检查点、调用与动作记录 |
| 评测入口 | 离线确定性验证与真实模型评测分开，输出 JSON 和 Markdown |

避免继续把全部职责追加到 loop.py。计量、工作区和运行服务单独成模块；现有护栏只在实现任务需要时提取，不做无关重构。

## 5. 阶段一：运行正确性

### 5.1 模型接入与依赖

- 将实际使用的 OpenAI Python SDK 声明为运行依赖，并覆盖客户端创建和响应解析路径。
- 模型名、兼容接口地址、密钥通过配置提供，保留现有智谱环境变量作为兼容入口。
- 本轮只支持一个配置驱动的 OpenAI 兼容客户端，不增加供应商路由与自动降级链。
- 显式区分离线演示、本地模型和远端模型模式。离线演示不创建网络客户端；本地模式默认只允许 loopback 地址，不要求真实 API key；远端模式默认禁用，本轮不启用。
- 所选模式缺少必要配置时任务提交在执行前明确拒绝，不能先创建 running 再后台失败。SDK 是接口依赖，安装 SDK 不等于获得免费模型服务。
- 离线单测、查看历史和进程健康检查不要求配置真实密钥。
- 模型输出协议校验、网络退避和失败原因保留；SDK 内外重试明确由一层控制，避免重试倍增。

### 5.2 统一预算与计量

- CLI、API、回归脚本使用同一计量与运行配置，默认累计 token 预算为 30,000。
- 累计用量来源唯一；恢复不能仅修改一个会被其他累计字段覆盖的别名。
- 每次成功收到模型响应即保存 prompt/completion/total token，包括无效决策和 planner 调用；失败 run 的已知用量同样保留。
- 无 usage 的模型响应不得静默按零收费：该调用标记 usage_unknown，暂停任务，返回明确原因。
- 请求结果丢失时标记该请求用量未知；报告已知累计值和未知调用次数，不声称是完整账单。
- 达到预算后不再发起下一次调用。请求前无法精确知道实际输入 token，文档明确最多可能出现已发出请求的实际用量越界。
- 批准续跑必须设置新的有限预算，新值大于已知累计用量；兼容旧 approve_budget=true 时，默认追加 30,000，审批记录保存前后预算。
- 计量、预算变化和调用次数持久化；不再通过批准开关永久禁用护栏。

### 5.3 完成判定

- done 必须建立在最近一次验证成功之上，且该验证晚于最后一次成功修改。
- pytest 退出码为 0、至少 1 个测试通过、无超时且测试基线完整时才视为验证成功。
- 未修改代码但原测试已通过的任务可以完成；零动作直接 done、零测试收集、修改后未验证均不能完成。
- 结果对象携带结构化 verified 字段，脚本不再通过“全绿”文本子串判断成功。
- GitHub 交付模式另要求记录成功创建的 PR；本地非 GitHub 分支不包装为已交付 PR。
- 写入 Python 语法检查失败应返回失败结果，先验证候选内容再替换文件，避免把已知语法错误直接写入。

### 5.4 计划与 MCP

- planner 已落库而尚无 checkpoint 时，恢复从已存 plan 重建上下文，不重复规划，也不丢计划。
- MCP 客户端、工具表与关闭逻辑由当前 run 持有。重连替换旧 handler，关闭后释放注册与进程；并发 run 不共享 MCP 闭包。
- 自定义 MCP server 配置中的命令实际参与启动，协议子集与配置范围写入文档。
- MCP 工具默认按未知副作用处理，只有明确配置为只读的工具可获 LOW 权限；保留 inputSchema 并做参数校验。
- HIGH 工具继续拒绝并审计。本轮不实现通用高危工具人工放行工作流。

## 6. 阶段二：工作区、状态和恢复

### 6.1 每 run 独立工作区

- 内置任务只允许从 tasks 根目录下已发现的合法任务包选择，不接受绝对路径、父级路径或越界符号链接。
- 新 run 复制任务包至数据目录下的 runs/<run_id>/workspace；基线及清单在该 workspace 之外保存。
- 源任务包只读，取消正常执行过程中的 git restore/git clean；完成或失败后保留 run 产物供检查。
- 排除 .git、.env、缓存、虚拟环境和数据产物，不沿符号链接或 Windows junction 复制外部文件。
- 同任务多个 run 使用不同目录。暂停 run 的现场不因新任务启动而重置。
- CLI --workspace 是操作者显式提供的本地源码来源，普通模式仍复制到私有工作区。
- GitHub 模式只接受显式开启的独立 Git 仓库，复制为 run 自有仓库，保留 origin 信息；源仓库与用户原有改动不受修改。
- 本轮保留产物，不自动递归删除历史 run；清理命令另行设计，不混入执行流程。

### 6.2 测试基线保护

- 初始化时记录原始测试、conftest.py 及 pytest 配置的路径和内容哈希。
- test_*.py、*_test.py、test/tests 目录、conftest.py、pytest.ini、pyproject.toml、setup.cfg、tox.ini 默认禁止通过 Agent 写工具改动。
- .git 元数据、.env、基线目录和运行管理文件同样不属于可写目标。
- 测试前及完成前检查基线；已有测试不可修改、删除或替换。检测到外部变更时停止并说明原因。
- 验证在临时执行目录中使用冻结测试基线，不把工作区里被替换的测试当成有效考卷。
- 此机制防止工具误改与常见评测投机，不声称能抵御任意 Python 程序的恶意篡改或逃逸。

### 6.3 运行状态与崩溃窗口

- 新 run 的状态为 pending → running → done/failed/paused/budget_paused/interrupted。
- 配置保存模型、预算、各能力开关、任务类型、工作区路径和格式版本；恢复默认复用原配置。
- 同一 run 的执行权通过数据库条件更新原子获取；进程内 _ACTIVE 只用于展示，不能作为唯一互斥来源。
- 每个 run 另持有操作系统文件锁，随进程退出释放；恢复 running 记录前必须成功取得该锁。无法取得返回冲突；成功取得且发现旧 running 记录时转 interrupted 并核查动作记录，不能推断上一动作未执行。
- 服务仍明确支持单 worker 部署；单 run 的 CLI/API 同时恢复请求只允许一个成功获取执行权。
- 重启不自动继续 running run，不自动花费 token，也不批量改写历史 run 状态。人工恢复时明确识别中断状态并检查现场。
- 工具开始前记录动作意图，工具结果、trace 与对应 checkpoint 在同一数据库事务中保存。
- 文件系统修改和数据库事务不能原子提交：若发现动作已开始但未完成记录，不自动重放写文件、提交、push 或创建 PR；返回 interrupted 与待核查动作。
- 已完成的检查点恢复时跳过已完成动作；外部副作用的不确定结果必须保留，不能假定失败并重试。
- 工作区 hash 使用相对路径与文件内容，排除运行生成缓存；不只使用 basename。
- 恢复中的漂移、配置不兼容、预算不足和未知动作都持久化错误码与说明，控制台重启后仍可看到。

### 6.4 历史兼容

- 用版本化迁移增加字段与新表，不删除或覆盖旧记录；通过 schema version 显式检查兼容性。
- 旧 run 缺少隔离工作区、配置或测试基线时标记 legacy，允许查看，不猜测恢复路径或重建测试来源。
- legacy 恢复在本轮不自动迁入；返回明确指引，用户可从同任务新建 run。
- 真实库首次升级必须执行显式备份与迁移；服务遇到旧 schema 时返回升级说明，不能悄悄升级真实库。
- 在测试副本中验证迁移幂等、旧记录保留、失败回滚与备份可读。

## 7. 阶段三：工程规范与服务边界

### 7.1 配置与依赖

- 添加 pyproject.toml，分运行与开发依赖；生成可安装验证的锁定依赖。不得把当前环境的无关包整体 freeze 当项目锁文件。
- 保留 requirements.txt 安装入口，文档和 Docker/CI 指向同一依赖来源。
- 配置至少包括数据目录、模型地址/名称/密钥、token 预算、模型/测试超时、API token、提交速率和日志格式。
- token_budget 范围为 1～1,000,000；测试和模型单次超时范围为 1～600 秒；非法值返回配置错误或 422，不进入执行线程。
- /health 只表示进程存活；新增 /ready 检查 schema、存储可写和当前运行模式所需配置。离线模式无需模型密钥；本地模式校验本地端点配置；缺配置时返回 503 且不泄露值。

### 7.2 API 与工具安全

- 配置 API_TOKEN 时，所有 /api 路由要求 Authorization: Bearer；使用常量时间比较。/health、/ready 返回最少必要信息。
- 默认本地模式允许不配置 API_TOKEN，监听及 compose 映射默认 127.0.0.1；文档明确外部使用必须配置鉴权与 HTTPS 反向代理。
- 控制台提供 token 输入，仅保存在页面内存，不写入 URL、localStorage、日志或错误信息。
- 提交与恢复端点共用进程内速率限制，默认每客户端每分钟 5 次，返回 429 和 Retry-After；最多记录 10,000 个客户端，清理超过 120 秒未使用的记录，容量仍满时拒绝新客户端的写请求。
- 不信任任意 X-Forwarded-For；不添加宽泛 CORS。goal 最长 20,000 字符、model 最长 128 字符、JSON 请求体最大 64 KiB；run 列表默认 30/最多 100 条，trace 默认 50/最多 200 条，超范围返回 422。
- 单机同时执行默认上限 2 个 run；超限返回 429，不建立没有 worker 的持久队列。
- 工具参数采用逐工具 schema 验证；未知或不合法参数返回可纠正错误。
- Git HTTPS 证书校验恢复默认；不读取或打印凭证，不在普通 run 全局开启 GitHub 能力。
- 测试子进程按白名单构造环境，剔除模型密钥、API token、GitHub token 和宿主 PYTHONPATH。
- 不将 run_tests 标注为无副作用的安全隔离；明确它执行任务代码，并限定输出、时间和进程树清理。

### 7.3 日志、CI 与 Docker

- 日志包含时间、级别、event、run_id、step、request_id；API 错误与运行异常保存稳定错误码。
- 密钥、Authorization、完整 prompt、源码正文默认不进入日志；模型错误先脱敏。
- 保留面向 CLI 的简洁输出，服务事件使用 logging，避免靠 print 作为唯一排错渠道。
- 所有质量检查均提供本地命令，包括 lint、format check、类型检查、pytest、覆盖率与确定性端到端验证。CI 配置保留同样命令，但本轮不触发可能计费的远端执行，不依赖云端 CI 完成本地验收。
- 覆盖率先测基线再设不能低于该基线的门槛，同时覆盖已确认缺陷；不使用未经测量的百分比冒充成果。
- 官方 MCP server 测试固定版本，与离线核心回归区分。
- Docker 排除密钥、数据、虚拟环境与本地 MCP node_modules；普通任务运行不再依赖镜像包含 .git。
- Docker 以非 root 用户运行；工作区与数据库同在持久卷，重建容器后可查看并恢复已保存任务。
- 镜像冒烟覆盖 SDK 导入、配置、/health、/ready 和离线任务闭环，不仅执行 --help。

## 8. 阶段四：评测与控制台

- 统一评测入口，保留旧脚本的兼容包装，输出带 schema_version、代码版本、配置、任务、原始尝试、重试和总用量的 JSON。
- 离线 suite 使用确定性决策器，覆盖 T1/T2/T3 修复、错误反馈、预算暂停/扩额、恢复、测试保护及失败路径。
- 真实模型 suite 独立运行，本轮只允许使用已有的本地模型；包含首次成功率与重试后成功率，失败尝试的耗时和 token 不丢弃。未配置本地模型时跳过并报告，不把离线结果作为真实模型成绩。
- 分别报告成功数/样本数、预算内完成率、已知 token、未知调用数、耗时与工具调用数，不以 done 数代替验证通过数。
- 上下文实验区分真实 API token 与本地估算；报告压缩率时同时报告任务正确性，不承诺截短不会丢语义。
- trace 查询分页；每步展示动作、结果摘要、用量及错误，回放定义为查看记录，不宣称重新执行可复现相同模型输出。
- 控制台展示 verified、持久化错误、interrupt/legacy 状态、预算及累计用量，只有可恢复状态才显示续跑入口。
- 渲染外部字符串使用 textContent 或统一转义；提交和恢复期间避免重复点击；轮询覆盖状态与历史列表。
- 更新 README、架构说明、部署说明与故障恢复说明，纠正文档中 MCP 帧历史、测试数及已移除文件位置。
- 交付记录明确列出：离线验证结果、真实模型结果、未执行检查和已知边界。
- 增加他人安装指南：环境准备、离线体验、本地模型配置、CLI 自带任务、取回结果与故障处理；不要求读源码或使用作者的密钥和私有路径。Web 导入导出指南随可选方案决定。

## 9. 验收矩阵

| 场景 | 期望 |
| --- | --- |
| 干净安装 | 所有运行依赖可导入，能运行离线闭环 |
| 无密钥离线体验 | CLI/Web 可体验固定任务闭环，明确标注演示，不产生模型网络请求 |
| 他人自带任务 | CLI 目录创建私有副本，修复结果可取回 |
| Web ZIP（若纳入） | 非法或超限包在解压前拒绝，不向目标工作区之外写文件 |
| 远端模型默认配置 | 请求被拒绝，不自动回退至任何远端模型 |
| 29,000 token 恢复后新增 100 | 累计为 29,100，历史不丢 |
| 默认 CLI/API | 同一预算、计量、完成与错误语义 |
| 预算达到上限 | 不再发下一次调用；有限扩额后可恢复 |
| 无动作 done/零测试 | 不接受完成 |
| 修改后未测试 | 不接受完成 |
| 改写或删除原测试 | 写工具拒绝；外部修改导致验证失败 |
| 同任务两次运行 | 工作区独立，源任务及暂停现场不变 |
| ../、绝对路径、链接越界 | 复制、工具读写和 API 入口均拒绝 |
| 相同 run 并发恢复 | 一个获得执行权，其余返回冲突 |
| checkpoint 边界中断 | 从已完成步骤之后恢复，配置和计量保留 |
| 工具副作用后、落库前中断 | interrupted，不自动重放副作用 |
| 已存 plan 无 checkpoint | 不重复规划且原计划重新注入 |
| MCP 连续运行/重连 | 当前 handler 使用当前 client，无跨 run 注册残留 |
| 未授权/提交过密 | 分别返回 401/429，不能启动模型调用 |
| 后台异常后刷新/重启 | 错误仍可查询，包含可理解说明 |
| 历史数据库副本迁移 | 原数据保留，幂等，可备份，可回滚 |
| Docker 仅保留持久卷后重建 | 工作区与 checkpoint 仍匹配，允许按规则恢复 |

## 10. 实施与审核约定

已进入 writing-plans，按“运行可靠性”和“工程交付”分别编写实施任务，任务内采用先失败回归、再最小修复、最后验证。实施前由用户审核书面计划。

建议由当前会话直接实施，避免在共享目录中并发修改 loop、存储和 API；如用户选择子 Agent 执行，再按技能拆分独立任务。

每阶段结束记录实际命令与结果。未完成或未运行的检查明确列出，不使用历史报告替代当前验收。不在设计阶段更改业务源码、安装依赖或修改真实数据库。
