## 1. 为什么 M4 先补 planner（自检结论 → 决策）

v2.2 §4 承诺了 `runtime/plan.py（任务拆 DAG…）`，但代码里没有 planner，README 架构树也悄悄删了这行。
这是**计划与实现之间唯一动到叙事的欠账**——JD 关键词"五大核心模块 ① 任务规划器"目前接不上（现 loop 是
单条 agentic 路径，LLM 每步自选工具，无独立规划阶段）。

**设计定稿（选项 A，控制在一个"不加戏"的度）：**

- **两段式：plan phase（一次规划调用）+ execute phase（现有 agentic loop 原样复用）。**
- 计划是**咨询性脚手架，不是硬状态机**——执行仍让 LLM 每步自选工具。诚实口径：
  "我做了 planner，但它是 advisory plan + agentic execution，不是 DAG 硬调度。"
  这样：不重造一个会与已打通的 self-repair 闭环打架的调度器，保住 6/6；又真把"规划器"接上。
- **计划注入初始 user 消息**（goal + 计划摘要），自动随 checkpoint 持久化 →
  **resume 不重规划、不重付规划 token**（与"压缩不损可恢复性"同理，干净）。
- 计划单独落 `plans` 表做审计/回放口径；planning tokens 计入 meter（预算护栏不被规划调用绕过）。
- 开关 `use_plan`，默认值与 A/B 结果绑定（见 §3 B3）。

## 6. 诚实口径（面试与文档统一）

- planner 是 advisory plan，不是 DAG 硬调度；执行仍 agentic、LLM 每步自主选工具。
- T1~T3 是短任务，规划额外成本是**下界**；与压缩同构——长任务才放大价值。A/B 如实报告，不承诺"规划让短任务更快"。
- 不引 LangGraph（延续 Q5 自研浓度叙事）。
- 预算护栏语义：planning tokens 计入预算，护栏不可被规划调用绕过。

## 7. 面试预演补充（对 planner 追问，2026-09-06 按背靠背口径练圆）

- **"planner 是不是只是多了一次 prompt？"**
  不只是，四处可证：① 规划是**结构化产出**（AgentPlan Pydantic 强校验，坏 JSON 重试 ≤2，耗尽降级无计划照跑——advisory 不拖垮 run）；② 计划**单独落 `plans` 表**（run_id / plan_json / planning_tokens），可审计可回放（现场可 `sqlite3` 查）；③ 计划**注入初始 user 消息、随 checkpoint 持久化**——进程被杀 resume **不重规划、不重付规划 token**；④ planning tokens 计入预算 meter，**护栏不可被规划调用绕过**。真机对照：一次规划 ~1k token，正是短任务的开销下界（见 Q3 数字）。
- **"为什么不把计划变成硬调度？"**
  保住 self-repair 是根因——硬 DAG 让执行无法按实测结果偏离原计划，而 6/6 恰恰建立在"跑红→自改→再验证"的闭环上（advisory 才允许偏离）。反面佐证来自 B6a：plan 档一局在长上下文里连续 5 步空转侦察、烧到 35,756 token 才被 30k 预算护栏截停为 budget_paused——这局虽发生在 429 高压期，却正面证明**护栏在 plan 场景照样生效**；若上硬调度只会放大这类空转。
- **"规划到底省没省钱？"**
  背靠背同批实测（glm-4.5-flash 免费）的诚实口径：**短任务不省 token、是纯开销**——总 token T1 +4,665 / T2 +1,952 / T3 +3,636；但 **T2（多文件侦察型）稳定省 1 步（6→5，2/2 复现），省步不省 token**。初版 A/B"T2 −953"是拿官方中位当对照的单次运气，背靠背已证伪。plan 还有隐藏成本：token 更高 → **更容易撞免费账户限流（智谱 1302）**。结论：默认关（数字① 口径不动），价值在长任务/复杂任务放大——与 context_compress 同构、按需开。延伸故事：正是 429 痛点催生了 O1 llm 韧性层（错误分级退避 + 熔断 + 限速），把"plan 更易撞限流"从坑变成又一个工程改进闭环。
