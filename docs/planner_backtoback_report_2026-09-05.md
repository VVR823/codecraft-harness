**关键观察**：
1. **plan 在账户健康期 6/6 全绿**（T1×2、T2×2、T3×2）→ plan 不破坏 self-repair，数字④ 前提成立。
2. 补测暴露的 3 个失败样本**全部发生在账户被 429 高压笼罩的时段**——免费模型服务端高压下质量退化
   （与 M1 期 glm-4-flash 过载、4.7-flash 弃用的现象同源），**不是 plan 逻辑带偏**。
3. 🔴 **新发现——plan 的隐藏成本**：plan 档比 no-plan 多一次规划调用 + 更长上下文 = 更高 token 消耗
   = **更容易撞免费账户限流**。同批 6 局连跑时，no-plan 3 局全绿、plan 第 2 局就开始空转/失败，
   plan 档对账户负载更敏感。

## 三、结论（数字④ 口径定稿）

1. **plan 不破坏 self-repair**：健康期 T1/T2/T3 均 2/2 全绿（共 6/6），补测失败样本归因限流污染。
2. **no-plan 基线稳定**：3 任务背靠背 3/3 全绿，与官方中位一致。
3. **token 收益不成立、步数微降**：B3 报告"T2 省 953 token"是单次运气（背靠背 T2 是 +1,952）；
   但 T2 plan 稳定 5 步 vs no-plan 6 步（2/2 复现），plan 在多文件侦察型任务上**省步数**的苗头真实存在。
4. **P5 默认关的论据升级**：不只是"短任务开销"（T1 +4.6k），更因为 **plan 放大免费模型的不稳定面**——
   免费档跑 plan 要多承担限流风险。默认关、长任务/付费模型按需开，是免费档的正确姿势。
5. **measure 场景护栏价值复证**：T2 plan 空转 35k 被 30k 预算截停——没有护栏，这次会无限烧下去。

## 四、附带修复（commit 9b151cd）

`measure_plan.py` 补两个缺陷（补测暴露）：
1. **无整局自愈重试**：429 账户级限流（智谱 code 1302，窗口可达数分钟）会 RuntimeError 冒泡崩掉整个脚本，
   崩前已跑局的结果也不落盘。修复：run_one 拆 _run_once，429/空内容类故障冷却 90s 整局重试 ≤2
   （run_all 同口径）；正常返回的 failed/budget_paused 不重试（那是真实信号，不掩盖）。
2. **失败不可区分**：budget_paused（护栏止损）与普通失败都报 green=False。修复：返回加 status 字段
   （done/failed/budget_paused/llm_failed），报告表加状态列。

另：原始数据 data/measure_plan_20260905_*.md 完整留档（gitignore），含全部失败样本 run_id 可回溯。
